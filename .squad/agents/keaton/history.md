### 2026-06-20T13:35:23-04:00 — Onboarding Script Fixes (from Hockney test report)

- Three bugs fixed in `scripts/setup-repo.ps1` based on Hockney's `docs/onboarding-test-report.md`.
- **Fix 1 (medium):** `Test-FileCustomized` regex broadened from `<[A-Z_]+>|<YOUR_|<GENERATE|_instructions` to `<[^>]+>|_instructions`. The old regex missed ~10 lowercase/mixed-case placeholders across the three templates (e.g. `<ISO8601 timestamp>`, `<UUID generated by Konnect...>`, `<Azure Key Vault name where...>`). A user who manually copied a template and removed `_instructions` without filling in lowercase values would have been falsely told their file was configured. The new regex catches any angle-bracket token regardless of case.
- **Fix 2 (low):** Wrapped `Copy-Item` in `try/catch` in Section 5. Previously a permission error (locked file system, UAC, etc.) would produce an unformatted PowerShell termination message and abort the script. Now it reports a clean ❌ message and lets the rest of the script continue.
- **Fix 3 (low):** After `Expand-Archive` for both `deck` and `kongctl`, script now checks if the binary landed at the expected path (`tools\deck\deck.exe` / `tools\konnect-cli\kongctl.exe`). If the zip had a top-level subdirectory, it uses `Get-ChildItem -Recurse` to locate the `.exe` and moves it to the expected path. If still not found, it emits a ⚠️ warning with manual guidance rather than silently leaving the binary in an unexpected location and re-downloading next run.
- **Pattern noted:** Always broaden template-detection regexes to be case-insensitive from the start; natural-language placeholder text in JSON templates will always include lowercase words.

### 2026-06-19T16:46:27-04:00 — JWT Bearer vs API Key for Key-Based Path

- Rob asked why the "key-based" MCP path uses Bearer tokens instead of a simpler API key mechanism.
- **Root cause of confusion:** "Key-based authentication" is *Foundry's* terminology for "anything that isn't OAuth." Under that umbrella, both a raw API key and a JWT Bearer token qualify as "key-based." They are different things in Kong's plugin model (`key-auth` vs `jwt`).
- **Why JWT was chosen:** Kong's `jwt` plugin was already in place for the `chat` service. It gave us token expiration (`exp` claim) even on the POC credential — a genuinely useful security control. Bearer token format is standard HTTP. No meaningful upside to switching.
- **What a Kong `key-auth` alternative would look like:** Replace the `jwt` plugin with `key-auth`. Foundry would send `X-API-Key: <static-string>` instead of `Authorization: Bearer <jwt>`. No signing required, but also no expiration — static credentials until manually rotated.
- **Foundry compatibility:** Foundry's key-based connection just replays a stored header name + value pair. It works equally well with `Authorization: Bearer <jwt>` or `X-API-Key: <key>`. No Foundry-side preference.
- **Conclusion:** Keep JWT Bearer for the key-based path. Expiration is worth the slight complexity of token generation. The naming ambiguity is a Foundry UX artifact — clarify in docs, not by changing the implementation.
- **Production note:** If we later want a pure API-key path with no expiry concern (e.g., server-to-server long-lived credential), `key-auth` is a valid second option to add alongside JWT — but not a replacement.
