### 2026-06-20 — Onboarding Script Test (`scripts/setup-repo.ps1`)

**Tested via:** static code analysis + live `-CheckOnly` execution (safe, read-only).

**Overall verdict:** Script is solid and safe. Clear output, idempotent, no secrets at risk.

**Key findings:**
- `Test-FileCustomized` regex `<[A-Z_]+>|<YOUR_|<GENERATE|_instructions` misses 10+ lowercase/mixed-case placeholder patterns (e.g. `<UUID generated by Konnect...>`, `<ISO8601 timestamp>`, `<CLIENT_SECRET — ...>`). A file copied from template without customization could be falsely reported as "configured". Fix: change to `<[^>]+>|_instructions`.
- `Copy-Item` in Section 5 is not wrapped in try/catch — a permission error would terminate with an unformatted PS error rather than a clean `Write-Fail` message.
- `-InstallTools` deck/kongctl download does not verify binary path after zip extraction. If the zip has a subdirectory, binary lands at the wrong path and the check re-triggers on next run.
- All docs referenced in the script and `docs/repo-setup.md` were verified to exist.
- Credential files (`api-key-config.json`, `entra-oauth-config.json`, `konnect-connection.json`) are all properly gitignored. `tools/` and `scripts/.generated/` also correctly excluded.
- Script is idempotent — re-runs are safe, existing files are never overwritten.
- `mock-api\node_modules` was the only missing item on the current dev machine (warn, not fail).

**Test report:** `docs/onboarding-test-report.md`

### 2026-06-19 — Phase 2: Key-Auth Route Validation

**Context:** Fenster deployed `/mcp/key/sse` and `/mcp/key/messages` routes with the `key-auth` plugin. Hockney executed full validation.

**API Key used:** `<REDACTED — see api-key-config.json>` (from `api-key-config.json`, consumer: `foundry-mcp-client`)

**All results: PASS across all categories.**

#### Authentication
- No key → HTTP 401, body `{"message":"No API key found in request"}` ✓
- Wrong key → HTTP 401, body `{"message":"Unauthorized"}` ✓
- Valid key → HTTP 200, SSE stream opens ✓

#### SSE Stream
- Valid key opens SSE connection (HTTP 200, `content-type: text/event-stream`) ✓
- Receives `event: endpoint` bootstrap event ✓
- Endpoint URL advertised as `/mcp/key/messages?sessionId=...` (**not** `/mcp/messages`) ✓ — this means the MCP server is advertising the correct key-route path, not the old path. The path rewrite strategy is working.

#### MCP Message Round-Trip
- `initialize` → HTTP 202, SSE delivers `mock-api-mcp-server` metadata ✓
- `tools/list` → returns `get_weather` and `calculate` ✓
- `tools/call get_weather(Seattle)` → structured JSON with location/temperature/condition ✓
- `tools/call calculate(6×7)` → result 42 ✓

#### CORS
- OPTIONS preflight returns HTTP 200 with `access-control-allow-origin: *`, `access-control-allow-headers` includes `X-API-Key` ✓
- GET with Origin header returns `access-control-allow-origin: *` and `access-control-expose-headers` ✓

#### Regression (JWT routes)
- Existing test suite: **10/10 PASS** ✓
- JWT routes `/mcp/sse` and `/mcp/messages` fully intact
- `/chat` (Azure OpenAI) working

#### OAuth Regression
- `/mcp/oauth/sse` returns HTTP 401 without auth — route is live and protected ✓

#### Edge Cases
- Key in `Authorization` header → 401 ✓ (correct rejection)
- Malformed short key → 401 ✓
- Key with leading/trailing whitespace → **PASSES** ⚠️ (Kong strips whitespace before key lookup — see inbox note)
- Key as query param (`?apikey=`) → 401 ✓ (`key_in_query: false` enforced)
- Empty `X-API-Key` header → 401, `No API key found` ✓

**Notable finding:** Kong strips leading/trailing whitespace from the `X-API-Key` value before matching. A padded key like `" <key> "` authenticates successfully. This is cosmetic for the POC but worth noting for any future strict credential format enforcement.
