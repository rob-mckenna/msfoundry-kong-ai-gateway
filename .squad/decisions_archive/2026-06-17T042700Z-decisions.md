### Decision 1: JWT Plugin Scoped to Chat Service + POC Consumer Added
**Author:** Fenster (API/Gateway Dev)  
**Date:** 2026-06-16T18:38:14-04:00  
**Status:** Proposed — awaiting Keaton review

**Context:** Keaton's ACA deployment assessment flagged a P0 blocker: the JWT plugin was declared in the global `plugins:` block with no consumers defined, causing Kong to return HTTP 401 on every proxied request.

**Decision:**
1. **Remove global JWT plugin.** The top-level `plugins:` section has been deleted from `kong.yaml`.
2. **Scope JWT to the `chat` service.** The `jwt` plugin entry now lives inside `services[chat].plugins[]`. It applies only to the `/chat` route. Any future routes (health checks, new model endpoints) will not inherit JWT enforcement unless explicitly added.
3. **Add a POC consumer with HS256 credential:**
   - Consumer username: `poc-user`
   - JWT key (issuer): `kong-poc`
   - Algorithm: `HS256`
   - Secret: `poc-secret-change-me` ← must be rotated before any non-local deployment

**Rationale:** Kong's JWT plugin requires at least one consumer with a matching credential in order to validate tokens. Service-level scope is the right granularity — easier to maintain as routes are added. Global JWT was too broad for a gateway that will eventually expose unauthenticated internal endpoints (e.g., a future `/health` passthrough).

**Follow-up Required:**
- [ ] Rotate `poc-secret-change-me` before any deployment beyond local Docker testing.
- [ ] Define real consumer/credential strategy (Azure AD tokens? API key + JWT bridge?) before the Foundry integration milestone.
- [ ] Consider moving credentials to a secrets manager and using `envsubst` at container startup.

### Decision 4: JWT Plugin Fix — Two Root Causes
**Author:** Fenster + Coordinator  
**Date:** 2026-06-17T03:05:00Z  
**Status:** Fixed

**What:** Fixed Kong JWT returning "No credentials found for given 'iss'" by addressing two issues:

1. **Plugin execution order**: Changed managed identity token injection from `pre-function` (priority 1000000, runs BEFORE jwt) to `post-function` (priority -1000, runs AFTER jwt). The pre-function was overwriting the Authorization header before JWT could validate the client token.

2. **Format version bug**: Changed `_format_version` from `"3.0"` to `"2.1"`. Kong 3.7's format_version 3.0 has a bug where `jwt_secrets` nested under `consumers` don't get properly indexed for credential lookup.

**Why:** Blocked end-to-end flow. Now working: client JWT → Kong validates → post-function injects managed identity token → Azure OpenAI processes request.

**Impact:** Full pipeline operational.

# MCP Gateway Architecture Proposal

**Author:** Keaton (Technical Lead)  
**Date:** 2026-06-17T04:02:00Z  
**Status:** Proposed — awaiting team review

---

## Executive Summary

This proposal extends our working Kong 3.7 AI Gateway deployment to support **Model Context Protocol (MCP)** integration with **Microsoft Foundry**. We will add two new Container Apps (Mock API + MCP Server) behind Kong's existing ingress, enabling Foundry models to call external tools via the MCP protocol over Server-Sent Events (SSE).

**Key architectural decisions:**
1. **Separate Container Apps** for Mock API and MCP Server (loose coupling, independent scaling)
2. **Path-based routing** at Kong (`/chat` for AI traffic, `/mcp/*` for MCP Gateway)
3. **SSE-optimized Kong configuration** (buffering disabled, connection timeout extended)
4. **Reuse JWT authentication** for MCP traffic (same `poc-user` consumer during POC phase)
5. **Internal ACA service discovery** for MCP Server → Mock API calls (via Container App environment DNS)

**Build order:** Mock API → MCP Server → Kong MCP routes → Foundry integration

---

## 1. Component Design

### 1.1 Mock API (Container App)

**Purpose:** Provide 2-3 simple REST endpoints that the MCP Server will wrap as MCP tools.

**Tech Stack:**
- **Runtime:** Node.js 22 LTS (Alpine-based for small image size)
- **Framework:** Express.js (minimal, well-understood, fast startup)
- **Endpoints:**
  - `GET /api/weather?location=<city>` — Returns mock weather data
  - `POST /api/calculate` — Body: `{ "operation": "add|subtract|multiply", "a": number, "b": number }` — Returns calculation result
  - `GET /api/status` — Health check (returns `200 OK`)

**Deployment Config:**
- **Image:** `<acr>.azurecr.io/mock-api:1.0`
- **Port:** 3000 (HTTP only, internal-only ingress)
- **Ingress:** Internal only (not exposed to internet)
- **Resources:** 0.25 CPU, 0.5Gi memory (minimal workload)
- **Scaling:** Min 1, max 3 replicas (low traffic expected)
- **Health probes:** Liveness + readiness on `/api/status`

**Rationale:** Express.js on Node.js is battle-tested, has minimal dependencies, and starts in <2 seconds. Internal-only ingress prevents accidental exposure; only the MCP Server needs to reach it.

---

### 1.2 MCP Server (Container App)

**Purpose:** Implement the Model Context Protocol, exposing the Mock API's endpoints as MCP tools. Handles SSE transport and tool invocation.

**Tech Stack:**
- **Runtime:** Node.js 22 LTS (Alpine)
- **SDK:** `@modelcontextprotocol/sdk` (official MCP SDK for Node.js)
- **Framework:** Express.js for HTTP server + `express-sse-middleware` or native `res.write()` for SSE streaming

**MCP Tool Schema Design:**

```json
{
  "tools": [
    {
      "name": "get_weather",
      "description": "Get current weather for a city",
      "inputSchema": {
        "type": "object",
        "properties": {
          "location": { "type": "string", "description": "City name" }
        },
        "required": ["location"]
      }
    },
    {
      "name": "calculate",
      "description": "Perform arithmetic calculation",
      "inputSchema": {
        "type": "object",
        "properties": {
          "operation": { "type": "string", "enum": ["add", "subtract", "multiply"] },
          "a": { "type": "number" },
          "b": { "type": "number" }
        },
        "required": ["operation", "a", "b"]
      }
    }
  ]
}
```

**Connection Handling:**
- SSE endpoint: `GET /mcp/sse` (long-lived connection)
- Tool execution: When Foundry calls a tool, MCP Server:
  1. Receives tool invocation via SSE
  2. Makes HTTP request to Mock API (e.g., `GET http://mock-api-internal.default.svc.cluster.local:3000/api/weather?location=Seattle`)
  3. Transforms response to MCP format
  4. Sends result back over SSE

**Deployment Config:**
- **Image:** `<acr>.azurecr.io/mcp-server:1.0`
- **Port:** 8080 (HTTP)
- **Ingress:** Internal only (Kong proxies public `/mcp/*` → internal MCP Server)
- **Resources:** 0.5 CPU, 1Gi memory (handles SSE connection state + HTTP requests)
- **Scaling:** Min 1, max 5 replicas
  - **Note:** SSE connections are stateful. Each connection pins to one replica. ACA's KEDA HTTP scaler will scale based on concurrent connections.
- **Health probes:** Liveness + readiness on `/health`
- **Connection timeout:** Ensure no application-level timeout; rely on Kong's proxy timeout settings

**Environment Variables:**
- `MOCK_API_URL`: `http://mock-api-internal.default.svc.cluster.local:3000` (or ACA internal FQDN)
- `PORT`: `8080`
- `NODE_ENV`: `production`

**Rationale:** The official `@modelcontextprotocol/sdk` handles MCP protocol details (handshake, tool discovery, execution). Separating MCP Server from Mock API allows independent scaling and future expansion (e.g., adding more MCP tools that call different backends).

---

### 1.3 Kong MCP Routes & Plugins

**Route Configuration (added to `kong.yaml`):**

```yaml
services:
  - name: mcp-service
    url: http://mcp-server-internal.default.svc.cluster.local:8080  # Internal ACA DNS name
    plugins:
      - name: jwt
        config:
          claims_to_verify:
            - exp
          uri_param_names:
            - jwt
          key_claim_name: iss
          secret_is_base64: false
      - name: rate-limiting
        config:
          minute: 100  # Lower than chat (SSE connections are long-lived)
          policy: local
      - name: cors
        config:
          origins:
            - "*"
          methods:
            - GET
            - POST
            - OPTIONS
          headers:
            - Authorization
            - Content-Type
            - Cache-Control
          exposed_headers:
            - X-Request-ID
          credentials: false
          max_age: 3600
    routes:
      - name: mcp-route
        paths:
          - "/mcp"
        strip_path: false  # Preserve /mcp prefix when proxying
        methods:
          - GET
          - POST
```

**SSE-Specific Kong Settings (Dockerfile or runtime env vars):**

Add these to Kong's environment variables in `infra/main.bicep`:

```bicep
{
  name: 'KONG_PROXY_BUFFERING'
  value: 'off'
}
{
  name: 'KONG_NGINX_HTTP_PROXY_BUFFERING'
  value: 'off'
}
{
  name: 'KONG_NGINX_PROXY_SEND_TIMEOUT'
  value: '600s'  # 10 minutes for long-lived SSE connections
}
{
  name: 'KONG_NGINX_PROXY_READ_TIMEOUT'
  value: '600s'
}
```

**Rationale:**
- **Buffering off:** Nginx (Kong's underlying proxy) buffers responses by default. SSE requires immediate forwarding of each event.
- **Extended timeouts:** SSE connections stay open for minutes or hours. Default timeouts (60s) would kill the connection prematurely.
- **JWT reuse:** Same `poc-user` consumer validates MCP traffic during POC. Production deployment should consider separate consumers or OAuth2 integration with Foundry's identity provider.
- **Rate limiting:** Lower limit (100/min vs 300/min for chat) because SSE connections are stateful and fewer in number.

## 2. Integration Points

### 2.1 Traffic Routing: MCP vs AI Chat

**Strategy:** Path-based routing at Kong

- **AI chat traffic:** `POST /chat` → Azure OpenAI (existing flow, unchanged)
- **MCP traffic:** `GET|POST /mcp/*` → MCP Server (new flow)

**Why path-based routing?**
- Single Kong ingress FQDN simplifies client configuration
- Clear separation of concerns (chat vs tool calling)
- Future expansion: add `/search`, `/embedding`, etc. without new ingress endpoints

**Alternative considered and rejected:** Separate domains (`chat.example.com`, `mcp.example.com`) — adds DNS complexity, separate TLS certs, more ingress costs in ACA.

---

### 2.2 Authentication Flow

**POC Phase (Current):**
- **Client → Kong:** Same JWT as chat flow (issuer `kong-poc`, HS256, secret `poc-secret-change-me`)
- **Kong → MCP Server:** No auth header passed downstream (internal traffic, trusted network)
- **MCP Server → Mock API:** No auth (both internal services)

**Production Considerations:**
1. **Rotate JWT secret** before Foundry integration
2. **Consider OAuth2 plugin** for Foundry (if Foundry supports client credentials flow)
3. **Add API key authentication** between Kong and MCP Server (using Kong's `key-auth` plugin) to prevent unauthorized internal calls if network segmentation is weak
4. **Managed identity for Mock API?** Not needed for POC (Mock API is internal), but if Mock API later calls Azure resources (e.g., Azure SQL, Blob Storage), add system-assigned identity and inject tokens similar to the `post-function` plugin in the chat service.

**Recommendation:** Keep JWT for POC, plan OAuth2 migration for production.

---

### 2.3 Service Discovery: MCP Server → Mock API

**Strategy:** ACA internal service DNS

Azure Container Apps provides built-in DNS resolution within the same Container App Environment:
- **Mock API internal FQDN:** `http://mock-api-internal.internal.<cae-default-domain>`
- **MCP Server** sets `MOCK_API_URL` environment variable to this FQDN

**Implementation in Bicep:**

```bicep
// Mock API Container App
resource mockApiApp 'Microsoft.App/containerApps@2024-03-01' = {
  name: 'mock-api-internal'
  properties: {
    configuration: {
      ingress: {
        external: false  // Internal only
        targetPort: 3000
      }
    }
  }
}

// MCP Server Container App
resource mcpServerApp 'Microsoft.App/containerApps@2024-03-01' = {
  properties: {
    template: {
      containers: [
        {
          env: [
            {
              name: 'MOCK_API_URL'
              value: 'http://mock-api-internal.internal.<cae-domain>'
            }
          ]
        }
      ]
    }
  }
}
```

**Alternative considered:** Hardcode IP addresses — rejected due to dynamic IPs in ACA. DNS is the correct pattern.

### 2.4 Kong → MCP Server Internal Routing

**Strategy:** Internal ingress on MCP Server, Kong proxies via internal FQDN

- **Kong service URL:** `http://mcp-server-internal.internal.<cae-domain>:8080`
- **Kong ingress:** Public (already exists)
- **MCP Server ingress:** Internal (not exposed to internet)

**Network flow:**
1. Client (Foundry) → Kong public FQDN (`https://kongai-gw.graycoast-a8631da5.eastus2.azurecontainerapps.io/mcp/sse`)
2. Kong → MCP Server internal FQDN (within ACA environment)
3. MCP Server → Mock API internal FQDN (within ACA environment)

**Security:** Only Kong is internet-facing. MCP Server and Mock API are only reachable within the Container App Environment.

## 3. Risk Assessment

### 3.1 SSE Proxying Through Kong

**Risk:** Kong (Nginx) buffers responses by default. SSE requires immediate event forwarding. Buffering will break the streaming flow.

**Mitigation:**
- Set `KONG_PROXY_BUFFERING=off` and `KONG_NGINX_HTTP_PROXY_BUFFERING=off` (done in section 1.3)
- Test with `curl -N https://<kong-fqdn>/mcp/sse` to verify events stream in real-time

**Risk:** Default proxy timeout (60s) will kill SSE connections prematurely.

**Mitigation:**
- Set `KONG_NGINX_PROXY_SEND_TIMEOUT=600s` and `KONG_NGINX_PROXY_READ_TIMEOUT=600s` (done in section 1.3)
- Monitor Kong logs for `upstream timed out` errors after deployment

**Risk:** Connection pooling may interfere with SSE (Nginx tries to reuse connections).

**Mitigation:**
- SSE uses long-lived connections; Nginx's connection pooling is designed for request/response cycles. Monitor for connection reuse issues.
- If problems arise, add `keepalive: 0` to Kong's upstream configuration (requires custom Nginx config or Kong plugin).

**Overall severity:** **MEDIUM**. SSE through Kong is well-documented, but requires specific Nginx tuning. We have the right settings; test early.

---

### 3.2 Long-Lived Connection Handling on ACA

**Risk:** ACA's KEDA HTTP scaler may not scale correctly for long-lived SSE connections (designed for short HTTP requests).

**Mitigation:**
- Set `minReplicas: 1` for MCP Server (always have capacity for at least one connection)
- Monitor ACA's scaling metrics (`HTTP Scaling Rule` based on `concurrentRequests`)
- Consider switching to manual scale rules (fixed replica count) if KEDA scaling is problematic

**Risk:** Cold start latency if MCP Server scales to zero (unlikely with `minReplicas: 1`, but possible in future).

**Mitigation:**
- Always keep `minReplicas: 1` for MCP Server
- Node.js + Express.js starts in ~2 seconds; acceptable latency for tool calls

**Risk:** ACA's default ingress timeout may interfere with SSE connections.

**Mitigation:**
- ACA ingress timeout is managed at the environment level, not per-app. Default is 240 seconds.
- Test SSE connections lasting >4 minutes. If timeout occurs, open Azure support ticket to increase environment-level timeout (not exposed in Bicep as of 2024-03-01 API version).

**Overall severity:** **MEDIUM-HIGH**. ACA's ingress timeout is the biggest unknown. Plan for early integration testing.

---

### 3.3 Microsoft Foundry → Kong MCP Integration

**Risk:** Protocol version mismatch. MCP is evolving; Foundry and `@modelcontextprotocol/sdk` may use different versions.

**Mitigation:**
- Use the latest stable `@modelcontextprotocol/sdk` version as of 2026-06-17
- Foundry team provides MCP client configuration (ask for supported protocol version)
- Plan for version negotiation in MCP handshake

**Risk:** Auth configuration. Foundry may require OAuth2 client credentials, not JWT.

**Mitigation:**
- Confirm auth requirements with Foundry team before production deployment
- Kong's `oauth2` plugin supports client credentials flow
- POC uses JWT for simplicity; production migration is straightforward

**Risk:** Error handling. MCP protocol may define specific error codes; Kong's default error responses (e.g., `502 Bad Gateway`) may not conform.

**Mitigation:**
- Add error transformation logic in MCP Server (catch upstream errors, format as MCP error responses)
- Test error cases (Mock API down, timeout, malformed tool invocation)

**Overall severity:** **LOW-MEDIUM**. Foundry team has integration docs; follow their guidance. Protocol mismatch is unlikely but plan for it.

---

### 3.4 Observability Gaps

**Risk:** SSE connections don't produce request/response pairs; traditional HTTP logging may miss errors.

**Mitigation:**
- Add structured logging in MCP Server for:
  - Connection open/close events
  - Tool invocation start/end
  - Upstream errors from Mock API
- Enable Application Insights for all Container Apps
- Add custom metrics (e.g., `mcp_connections_active`, `mcp_tool_calls_total`)

**Risk:** Debugging SSE issues requires inspecting streaming payloads, not just HTTP status codes.

**Mitigation:**
- Add verbose debug logging mode in MCP Server (`LOG_LEVEL=debug`)
- Use `curl -N https://<kong-fqdn>/mcp/sse --header "Authorization: Bearer <jwt>"` for manual testing
- Consider adding a `/mcp/debug` endpoint (authenticated) that dumps current connection state

**Overall severity:** **LOW**. Observability is table stakes; plan for it upfront.

### 5.4 Foundry Integration (End-to-End)

**Prerequisite:** Foundry team provides test credentials and MCP endpoint configuration.

**Test cases:**
1. **Tool discovery:** Foundry connects to Kong MCP Gateway, retrieves tool list
2. **Successful tool call:** Foundry model invokes `get_weather`, receives result, incorporates it in response
3. **Error handling:** Foundry invokes tool with invalid parameters, receives MCP error response
4. **Auth failure:** Foundry attempts to connect with invalid JWT, Kong returns 401
5. **Rate limiting:** Foundry makes >100 requests/minute, Kong returns 429

**Tools:** Foundry's built-in testing tools + manual verification with Foundry AI model chat interface.

## 6. Recommendations

### 6.1 Should Mock API and MCP Server be separate Container Apps?

**Recommendation: YES, keep them separate.**

**Rationale:**
- **Independent scaling:** Mock API is stateless HTTP (scales on request count). MCP Server is stateful SSE (scales on connection count). Different scaling profiles require separate apps.
- **Loose coupling:** If we later add more MCP tools that call different backends (e.g., Azure SQL, Blob Storage), MCP Server doesn't need to change. Mock API can be swapped out without redeploying MCP Server.
- **Security isolation:** If Mock API later calls external services (e.g., third-party APIs), security policies can be applied at the Container App level (network policies, managed identity) without affecting MCP Server.

**Alternative considered:** Combined app (Mock API + MCP Server in one container). Rejected because it tightly couples two components with different lifecycles and scaling needs.

---

### 6.2 Should we enable Kong Admin API internally?

**Recommendation: YES, enable Admin API on internal-only port for debugging.**

**Rationale:**
- Kong's Admin API allows runtime inspection of routes, plugins, and upstreams (e.g., `curl http://localhost:8001/routes`)
- Useful for debugging MCP route issues without redeploying Kong
- Internal-only port (e.g., 8001) is not exposed to internet; only accessible from within ACA environment

**Implementation:**
- Update `infra/main.bicep`:
  ```bicep
  {
    name: 'KONG_ADMIN_LISTEN'
    value: '0.0.0.0:8001'  // Enable Admin API on port 8001
  }
  ```
- **Do not expose port 8001 in ACA ingress** (keep it internal)
- Access Admin API from Kong container's console or via Azure Container Apps `az containerapp exec`

**Security note:** Admin API is read/write by default. If enabled, restrict access via `KONG_ADMIN_GUI_ACCESS_LOG` or use Kong's RBAC (Enterprise only). For POC, internal-only access is sufficient.

### 6.3 Infrastructure Changes Needed

**Networking:**
- No changes required. ACA internal DNS and ingress handle service-to-service communication.
- If Foundry is on-premises or in a different VNet, ensure ACA environment allows inbound traffic from Foundry's IP range (Azure Firewall or NSG rules).

**Identity:**
- Kong already has system-assigned managed identity for Azure OpenAI access (unchanged)
- MCP Server and Mock API do not need managed identities for POC (no Azure resource access)

**Ingress:**

**Secrets:**

**Bicep structure:**

  - `infra/mock-api.bicep` (Mock API Container App)

**No other infrastructure changes required.** The existing ACR, Log Analytics, and Container App Environment are sufficient.
